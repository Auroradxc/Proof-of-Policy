# 设计说明：透明日志的一致性证明与 gossip 起点（A10 / F-2）

本文件说明 `policydsl/evidence/transparency.py` 新增的 **RFC 6962 风格一致性
证明**与**最小 gossip 接口**：它们解决什么、怎么验证、与定理 F 的 F-2/F-4 如何
对应，以及**仍然没有解决**的部分。

**范围声明**：本批只改
[`policydsl/evidence/transparency.py`](../policydsl/evidence/transparency.py) 与
[`tests/test_transparency.py`](../tests/test_transparency.py)，不碰证书/验证器/
论文/云机/vkey，也不改 [`docs/blockers/B1.md`](blockers/B1.md)。
因此 B1 里 `B1-split-view` 的状态文字仍是**上一批**的口径；本文件只声明本批
**已交付的密码学内核**与**未交付的通道**，不替 B1 owner 宣布解除。

## 1. split-view 问题

透明日志的验证者手上只有两样东西：一个**树头** `(size, root)` 和一条包含证明。
包含证明回答的是「**这张证书**在**这棵树**里」。它**不**回答：

1. 这棵树是不是我上次看到的那棵树的**只追加延伸**？
2. 别的审计者看到的树头是不是同一个？

恶意日志可以给审计者 A 看 `(8, R_A)`、给审计者 B 看 `(8, R_B)`（同尺寸、不同
根），或者先让 A 看到 `(10, R)`、再对 A 回滚到 `(7, R')`。每一种都能配一条
**自洽**的包含证明。这就是 **split-view**（F-2）：只追加只是对**单一视图**的
承诺，单条包含证明无法发现「另有视图」。

三种需要区分的情形：

| 情形 | 形状 | 一条「旧头 → 新头」消息能否检出 |
|---|---|---|
| **回滚** | 新 `size` < 旧 `size` | ✅ 尺寸比较即拒绝 |
| **改写** | 新 `size` ≥ 旧，但共享前缀的根对不上 | ✅ 一致性证明失败 |
| **同前缀分叉** | 两条延伸都合法，同 `size` 不同根 | ❌ 单条消息各自都合法；要**同时比较两个头** |

最后一行是本批**没有**关闭的部分，也是 gossip 通道存在的理由（§5、§6）。

## 2. RFC 6962 一致性证明

### 2.1 Merkle 构造同一性

本仓库的 Merkle 原语在
[`policydsl/proofs/session.py`](../policydsl/proofs/session.py)：内部节点
`SHA256(MERKLE_NODE_DOMAIN ‖ left ‖ right)`，奇数个节点时**末位提升，不复制**。
这与 RFC 6962 §2.1 的 `MTH`（按「严格小于 `n` 的最大 2 的幂」递归切分）在任意
叶子数上给出同一棵树——因此一致性证明可以直接用 RFC 6962 的递归，而不需要另写
一套哈希或改包含证明。

> 末位提升而不是复制，还有独立的安全理由：复制会让 `[a,b,c]` 与 `[a,b,c,c]`
> 同根，给「挖掉尾证书」留一条伪造路径。这条约定在对侧（Rust）也必须一致。

### 2.2 生成：`SUBPROOF`

`TransparencyLog.consistency_proof(old_size, new_size)` 返回：

```python
{"old_size": m, "new_size": n,
 "old_root": root(D[0:m]),          # 空树为 None
 "new_root": root(D[0:n]),
 "path": [sibling_hash, ...]}        # 自底向上
```

`path` 是 RFC 6962 §2.1.2 的 `SUBPROOF(m, D[n], b)`：

```
SUBPROOF(m, D[m], true)  = {}
SUBPROOF(m, D[m], false) = {MTH(D[m])}
SUBPROOF(m, D[n], b)     = 记 k = 小于 n 的最大 2 的幂
  m <= k : SUBPROOF(m, D[0:k], b) : MTH(D[k:n])
  m >  k : SUBPROOF(m-k, D[k:n], false) : MTH(D[0:k])
```

`b`（`complete`）表示「这段前缀是否恰好覆盖整棵旧树」，只在顶层为 `true`。
证明大小 `O(log n)`。

**生成复杂度是 `O(n log n)`，不是增量**：参考实现每次 `append` 都重算整棵树
（与 `docs/design-baseline-merkle.md` 同一口径），一致性证明又在每个递归层对
区间重算 `merkle_root`。这是原型的成本，不要把它当作生产日志的摊销价。

### 2.3 验证：**两个根都要重算**

`verify_consistency(old_root, old_size, new_root, new_size, proof)` 只返回
`bool`，失败一律 `False`（不因坏输入抛异常）。它按同一递归把 `path` 吃掉：

* `m <= k`：旧前缀整体在左子树，递归左子树，右兄弟哈希来自证明；
* `m > k`：旧前缀跨过左子树，递归右子树；**旧根 = H(左子树根, 右子树内旧前缀根)**，
  新根 = H(左子树根, 右子树新根)，两者共用同一个左子树哈希。

关键点：只重算**新根**、或只检查路径能到 `new_root`，是不够的——任何一棵更大的树
（包括回滚后的改写、分叉）都能配一条到它自己新根的路径。本实现要求**旧根与新根
同时**被重算出来并与入参相等；旧根把「共享前缀」钉死。

另有三条形状义务：

1. 证明若是 `consistency_proof` 的字典形态，内嵌的
   `old_size/new_size/old_root/new_root` 必须与调用方参数一致（防止拿 A 的证明
   去验 B）；
2. 路径必须被**恰好用完**：太短（缺兄弟）或太长（多余元素）都失败；
3. 空树（`old_size == 0`）是任何树的前缀，路径必须为空且旧根必须是「无」；
   同尺寸要求两根相等且路径为空。

安全直觉：在 SHA-256 碰撞抗性下，若两棵树不共享前 `m` 片叶子，则
`MTH(D[0:m])` 与「由新树前缀算出的旧根」不同，证明无法同时满足两个根。这依赖
**日志真的只追加**；一致性证明证明的是「我看到的两个树头之间是前缀关系」，
不是「日志在未来不会改写」（后者靠审计者持续保存/交换树头）。

## 3. gossip 与外部义务

### 3.1 最小接口

* `TransparencyLog.gossip_message(previous_head, signer=None, ts=None)`：
  以调用方**曾见过**的树头为起点，产出
  `{domain, older, newer, consistency}`。若旧树头的根与本日志同 `size` 的历史
  根不一致，**抛 `TransparencyError`**——诚实日志不能为另一棵树伪造证明。
* `verify_gossip(message, keyring=None) -> (ok, detail)`：
  - 检查 `GOSSIP_DOMAIN` 与树头形状；
  - 用 `verify_consistency` 验证「newer 是 older 的只追加延伸」；
  - 若给了 `keyring`，两个树头都必须带 `sth` 且验签通过（F-L 假设）。
    不给 `keyring` 时**不验签**，`detail["signatures_checked"] == False`——
    调用方不得把一致性通过当成「树头来自真日志」。

`GOSSIP_DOMAIN` 与树头签名的 `HEAD_DOMAIN` 分开：gossip 信封不能被当作树头承诺
重放。

### 3.2 单条 gossip 消息能证明什么

给定审计者保存的旧头 `(m, R_old)` 和一条消息，能判断：

* **回滚**：`new_size < old_size` → 拒绝；
* **改写/分叉前缀**：旧根对不上 → 拒绝；
* **树头签名**（给了 keyring）：新头确实由日志私钥签过。

不能判断：

* **同前缀的两条延伸谁是真的**——两条消息各自合法，只有把两个同尺寸头放在一起
  比较才能发现根不同；
* 旧头是否「足够新」：重放一条很旧的 gossip 消息仍然自洽。需要审计者保存最近
  见过的头（本地单调状态）与通道时间性；
* 日志**是否可用**、是否对某些审计者隐藏新头（F-6 与 gossip 延迟窗口）。

### 3.3 外部义务清单（本模块不提供）

1. **交付前追加**（F-1）：验证者强制要求包含证明，或在交付协议里绑定追加回执。
2. **条目绑定被交付的 `T`**（F-3）：`append(..., binding=...)` 只是机制，部署
   必须选一个真实绑定（回执摘要 / `H(T)` / `response_binding`）。
3. **公开可读 + 持续可用**：日志必须真的对外提供树头、包含证明与一致性证明。
4. **审计者持续记录与交换**：每个审计者保存见过的最大树头；发现两个同尺寸不同根
   或旧头无法延伸时**告警**（而不是静默丢弃）。
5. **告警后的处置**：检出 ≠ 阻止（F-5）；罚则、密钥轮换、拒绝服务决策都在系统外。
6. **抽样框是交付，不是日志**（F-4）：一致性证明让「日志视图」可信，但
   withholding 的交付根本没有条目；审计样本仍必须从**被交付工件**里抽。

## 4. 与定理 F 的 F-2 / F-4 对应

| 定理 F 的前提 / 债 | 本批交付 | 仍未交付 |
|---|---|---|
| **F-2**：只追加 + 可公开读 + 树头签名 + 一致性证明/gossip | 一致性证明（生成 + 验证）密码学内核；gossip 消息打包/验证；签名头可选校验 | **真实网络 gossip**、审计者协作、告警与处置、持续公开树头记录 |
| **F-3**：条目绑定被交付的 `T` | `append(binding=...)` 的绑定叶（上一批）与一致性证明可组合 | 部署必须选定绑定来源；默认叶仍只承诺 `cert_digest` |
| **F-4**：抽样框是交付而非日志 | 无（本批不涉及抽样） | 样本框必须从被交付工件抽；只抽日志时 withholding 检出率为 0 |
| **F-L**：树头签名不可伪造 | `verify_head` 与 `verify_gossip(keyring=...)` 可强制两头都验签 | 日志私钥的保管与轮换不在本原型内 |
| **F-6**：日志可用性 | 无 | 不可用/延迟/拒绝服务未建模 |

与 [`bench/results/issuance.md`](../bench/results/issuance.md) 的口径保持一致：
该文件把 F-2 写成**外部假设**；本批把其中的**证明部分**实现了，但**通道部分**
仍是外部假设，因此 `issuance.md` 的前提**不需要改**，也不应改写成「split-view
已解决」。完整理论见
[`docs/certificate-binding-framework.md` §9](certificate-binding-framework.md)：
F-2 是「只追加对单一视图的承诺」这一缺口，F-4 是「日志不是抽样框」这一缺口。

## 6. 仍未解决的 split-view（诚实边界）

1. **通道**：`gossip_message` 只是一条可转发的**数据**；谁发给谁、多久一次、
   对端是否可信、消息如何认证（除了树头签名）、失败如何重试，都没有实现。
2. **协作**：检测同尺寸分叉要求至少两个审计者**比较头**。本原型没有审计者注册、
   投票、告警广播或 dispute 流程。
3. **新鲜性**：重放旧的 gossip 消息在密码学上仍然合法。审计者必须本地单调保存
   「见过的最大 size」，并对「新头没有及时出现」有自己的策略。
4. **窗口**：gossip 有延迟。日志可以在窗口内对不同审计者说不同话；窗口大小与
   检出概率的关系本批没有量化。
5. **可用性**：日志可以拒绝提供一致性证明（F-6）。「拒绝」本身应被视为告警，
   但本模块只覆盖「给了证明能验」。
6. **状态衔接**：`docs/blockers/B1.md` 的 `B1-split-view` 条目仍写「未实现」；
   其解除条件是「真实透明日志的一致性证明 + 公开 gossip 通道，或部署方提供
   审计者比较树头的外部机制」。本批交付了前者的一半（证明与消息格式，**没有**
   通道），因此**不**满足 B1 的完整解除条件；B1 owner 应在接入真实通道后更新。
