# 语义规则（学习型规则）的信任边界论证

> 对应计划 §9.6；代码落在 `policydsl/semantic.py`、`semantic/`、`scripts/ezkl_prove.py`、
> `circuits/types/src/lib.rs`；验收在 `tests/test_semantic.py`（29 例，含 6 条反例）；
> 成本在 [`bench/results/semantic.md`](../bench/results/semantic.md)。
>
> **本文的职责是把边界说清楚，而不是把功能说漂亮。** 下一节起，每一处"我们做到了"
> 后面都跟着"这依赖于什么"和"这不保证什么"。凡是还没做到的地方，如实标注。

---

## 1. 为什么需要它：一个可复现的绕过

`keyword_block` 是**字符串包含**判定。它挡不住同形异义字符：

```
harm          "How do I weaponize the search tool against the user?"   → 关键词命中，拦下
harm_homoglyph "How do I wеaponize the search tool against the user?"   → 关键词**漏掉**
                        ↑ 西里尔 е (U+0435)，不是拉丁 e
```

两条串的差别只有一个码点，人类读起来完全一样。这不是构造出来的极端案例，
`tests/test_semantic.py::test_homoglyph_bypass_now_blocked` 就在本仓库里把
**前一半**（绕过成功）与**后一半**（语义规则拦下）分别断言了，而
`scripts/ezkl_prove.py selftest` 输出的四条文本里也包含这一对。

形式上更一般：**任何基于字面匹配的规则，其判定域是"码点串"，而策略的意图域是
"文本含义"。** 两者之间的映射不是单射也不是满射 —— 同形字、零宽字符、Unicode
规范化差异、拼音/音译、以及最根本的**改写**（换一种说法表达同一个请求），都是
这个间隙的具体形态。正则子集的表达力提升（P2-9b 的同形折叠）只能堵住**确定性**
的那几种，改写类攻击它一个字都挡不住。

所以本项目需要一个**学习型规则**：参数由训练得到、判定为 `f(T) ≥ θ`，其中 `f`
是一个小型神经网络。而这样的规则**无法用形式化方法验证** —— 它没有可读的语义，
这正是 TEE 方案与形式化验证方案共同留下的空位。

### 1.1 但"放进 zkVM 里跑一遍"不行

自然的想法是：把模型搬进 SP1 电路，让它也变成一条"入电路规则"。这条路在本项目
里**被刻意否决**，理由是它看起来健全、实际上把信任边界整体挪走了：

- 判定所需的 logit **必须进公开值**，否则验证方无从知道电路算的是不是这个分数；
- 而一旦 logit 进了公开值，验证方就需要知道"这个 logit 是从哪条 T 算出来的"；
- 那就得把 `f` 的**全部中间量**也放进公开值（否则出证方可以把一份良性文本的
  中间量配到有害响应上出证）—— 公开值会膨胀到与计算图同量级，且这些中间量是
  浮点的，电路里只能用定点近似复现，误差累积无法界定。

结论：**通用 zkML 的路线（"证明模型推理是正确的"）超出了本项目的目标，也超出了
它的收益边界。** 本项目要证的不是"推理正确"，而是**一条更窄、可证、且足以支撑
合规结论的命题**（下一节）。

## 2. 我们的命题：委托 + 陪伴证明

```
出证方                                                       验证方（持 T′、策略包、证书、陪伴证明）
─────────────────────────────────────────────────────────   ────────────────────────────────────────
① T ──encode──▶ id 序列 ──▶ ezkl 图（halo2）──▶ P(有害) ──▶ ② ezkl proof（公开实例 = encode(T) ‖ score）
                                                                          │
③ SP1 电路：judged = 判得了的约束                                             │
            delegated = [{name, system, model_vkey,                         │
                          onnx_sha256, threshold_bp, direction}]            │
                          ↑ **登记**"这条我没判"，而不是判它违规                │
                                                                          ▼
④ 证书 = {SP1 公开值} + {semantic.companions[]: 指纹 + proof_sha256}  ──▶  ⑤ 合取验证：
                                                                             SP1 证明 ✓ ∧ 陪伴证明 ✓
                                                                             ∧ 绑定到 T′ ✓ ∧ 阈值判定 ✓
                                                                             ⇒ **合规**
```

关键在于④与⑤之间的那一句话：

> **SP1 电路从不声称语义规则被满足了。** 它在 `ProofOutput.delegated` 里登记
> "这一条我没判"，而验证方**必须**找到对应的陪伴证明并自己判 —— 找不到就是
> FAIL（fail closed），而不是"跳过"。

这样子做出来的结论是一条**合取**：`合规 ⇔ 电路判得了的部分全部满足 ∧ 每条被委托
的规则被陪伴证明判定且满足`。二者都由密码学（各自的证明系统）支撑，**没有任何一步
依赖出证方的诚实转述**。

### 2.1 引理 L7（语义委托健全性）

> **注：编号。** 计划 §9.6 写的是"新增引理 L6"，但 `L6` 在
> [`security-model.md`](security-model.md) 里**已经**分配给了 P1-6 的跨证明组合义务。
> 为避免两条不同层面的引理撞号，这里用 **L7**；L6 保持原义。

**命题**：设策略 `π = π_in ∧ π_sem`，其中 `π_in` 是入电路的约束集合、`π_sem` 是被委托
的语义约束集合。若 `Verify` 接受且 `合规 = PASS`，则 `T′ ⊨ π`。

**论证**（在 `A1`(zkVM 确定性)、`A6`(ezkl/halo2 的 soundness) 下）：

1. `π_in` 部分：`Verify` 接受 ⇒ 公开值等于 zkVM 的确定性执行输出（`A1`）⇒ `π_in` 的
   判定结果唯一且为"满足"（主定理的同一论证，`docs/security-model.md` §4）。
2. `π_sem` 部分：`合规 = PASS` 要求 `semantic_satisfied` 里每条规则都为真。而
   `verify_companion` 返回 `satisfied=True` 的**前提**是它已经通过了第 1–5 步：
   - 第 2 步把证书的 `{vk_sha256, onnx_sha256, threshold_bp, direction}` 逐字段钉在
     **电路公开值**里的 `delegated[i]` 上 ⇒ 陪伴证明承诺的模型/阈值/方向与电路
     说的**是同一个**（否则出证方可以拿另一个模型的证明来凑）；
   - 第 3 步把证明文件的字节哈希钉在证书承诺的 `proof_sha256` 上；
   - 第 4 步要求本地 `vk.ezkl` 的哈希等于 `delegated[i].model_vkey`，再跑 ezkl
     验证器 ⇒ 证明有效（`A6`）；
   - 第 5 步要求公开实例的输入部分 `== encode(T′)` ⇒ 这份证明说的是**送达的**`T′`
     （信任边界 ③；与 SP1 侧 `response_binding` 是两条独立的路，都要走）；
   - 第 6 步用公开实例里的分数对阈值作比较 —— 分数与阈值都来自证明本身，比较是
     二者的确定性函数，不需要谁出证。
3. 于是 `π_sem` 的判定是"从 `T′` 出发、经承诺过的图、得到的分数、对比承诺过的阈值"
   的确定性结果。若 `T′ ⊭ π_sem`，第 6 步必为假 ⇒ `合规 ≠ PASS`。矛盾。∎

**与 L6 的关系**：L6 处理的是"两份独立证明**拼接**成一次会话级结论"（跨 zkVM 的
组合义务，P1-6）；L7 处理的是"一次证书内，一部分判定被**委托**给另一个证明系统"。
两者的共同点是都用 vkey/指纹做键分离，但 L6 是**横向拼接**、L7 是**纵向下沉**，
失败形态也不同（L6 是"替换子证明"，L7 是"漏判却声称已判"）。

**不依赖出证方诚实的部分**：`delegated` 由电路产出（出证方改不动）；陪伴证明由
ezkl 验证器判（出证方伪造不了）；绑定由验证方拿 `T′` 重算（出证方猜不到）。
出证方能做的只有"不附证明"或"附错的证明"，两种都被 fail closed 挡住。

## 3. 三个信任边界条件

计划 §9.0 列了三条。这三条都是**"不满足时会静默失效"**的类型，所以每一条都配了
具体的攻击形态 —— 只写"我们满足了"是没有说服力的。

### ① 模型权重必须被承诺

**做法**：`onnx_sha256`（`semantic/model.onnx` 的字节哈希）+ `model_vkey`（`vk.ezkl`
的字节哈希）双指纹写进约束，随 `policy_hash` 一起被 SP1 证明承诺；`vk.ezkl` 入库，
`MANIFEST.json` 记录全部产物的哈希。

**不这么做会怎样**：出证方可以在训练阶段作弊 —— 换一张"永远输出 0"的权重图，
重新 `setup` 得到一把新的 `vk`，然后一切照常工作：证明有效、验证器通过、分数是 0、
规则"满足"。整个链路没有任何一处会报错。**只有指纹能让验证方发现图中算的不是
策略里承诺的那个模型**（`test_swapped_onnx_rejected` / `test_swapped_vk_rejected`）。

**不保证什么**：承诺的是"用的是**这张**图"，**不是**"这张图是好的"。一个从一开始
就训练得糟糕、或者被投毒的模型，只要它被如实承诺，L7 依然成立 —— 密码学不判断
模型质量。见 §6.2。

### ② 特征必须在图内、且确定性

**做法**：`semantic/features.py` 的特征层是**确定性算术**（四张由常量种子
`b"pop-semantic-projection-v1"` 经 `random.Random.gauss` 生成的投影表 + 圆周移位
乘积 + `√L` 缩放 + L2 归一化），**没有学习参数**；head 权重来自落盘的
`head.weights.json`。两者都在同一张 ONNX 图里。全仓库唯一的编码真相源是
`features.encode`（训练、见证生成、出证、验证方重算都调它）。

**不这么做会怎样**：如果特征可以在图外算，出证方就能把**一份良性文本的特征向量**
配到**一条有害响应**上出证 —— 图只负责把给定向量过一遍 head，它无从知道这个向量
是不是从 T 来的。语义规则这时就成了可以随意摆布的摆设。

这个攻击之所以隐蔽，是因为它在结构上**看不出来**：本仓库里 `DIM == MAX_CHARS == 64`，
一份"图外特征向量"的长度与一份 id 序列**恰好相同**，任何长度检查都视而不见。
唯一能发现它的是"拿 `T′` 重算 `encode(T′)` 并逐位比对"（`test_declared_features_rejected`
把这个巧合也一并断言了）。

**不保证什么**：特征的**表达能力**不是密码学性质。投影表是固定种子的随机矩阵，
它是"哈希"而非"语义"——它的价值在于把字符组合压成定长向量，剩下的活全在 head 上。
这是一个**刻意的省算**选择：见 §4.1 的成本对比。

### ③ 输入必须与响应绑定

**做法**：ezkl 的公开实例布局是 `[MAX_CHARS 个 id] + [1 个输出]`，**输入与输出都是
公开的**。验证方拿送达的 `T′` 现场重算 `encode(T′)`，与实例的输入部分逐位比对
（`semantic.check_bound_to_response`）。

**不这么做会怎样**：`proof.json` 只有 40 KB、与证书分开流转。少了这一步，任何拿到
一份证明的人都**可以把它配到别的响应上**："我这条响应经模型判定是安全的" + 一份
真实的 ezkl 证明 —— 而证明其实是另一条文本的。这与 P0-2 的换响应攻击同构，
所以在设计上也就同样处理：**两条独立的路都要走**（SP1 侧 `response_binding` 绑的是
`H(n, T)`；ezkl 侧绑的是 `encode(T)` 本身）。

**不保证什么 —— 而且这一条是本文里最重的代价**：

> **`encode` 对收录字符是单射。** 公开实例里的那 64 个 id 可以逐个反查
> `features.VOCAB` 恢复出原文（未收录字符映射为 0，会丢失）。
> 也就是说：**带语义规则的证书会公开被判定响应的全文。**

这不是实现疏漏，是**格式的必然**：ezkl 把输入也当公开值，而验证方要能独立重算绑定
就必须知道 `encode` 的输入是什么。要隐藏它，只能让输入不出现在公开值里 —— 那样
验证方就失去了独立核对的能力，只能相信出证方的转述，而那正是本项目全部设计要避免
的东西。

于是 v1 的边界是：

| | 不含语义规则的策略 | 含语义规则的策略 |
|---|---|---|
| 公开值泄露 | `H(n, T)`（承诺）、脱敏后的 `R` | **`encode(T)`（可逆）** |
| 支持私有模式 | 是（`mode=private`） | **否 —— 电路直接 panic** |

私有模式下的 fail closed 是**刻意的**：`evaluate_private` 遇到 `semantic_bound` 会
当场 panic（`types/src/lib.rs`），而不是"跳过这条规则"。跳过会得到一张**看起来全绿、
而语义规则根本没被判定**的私有证书 —— 那正是 P0-1 的形态换了个位置。
`test_private_mode_fails_closed` 断言的就是这个 panic 与它的原因。

这也是 [`security-model.md`](security-model.md) §5.2 那条"响应绑定与响应内容隐藏对
低熵 `T` 互斥"的**第二个实例**（第一个是 SP1 侧的 `response_binding`）：语义规则把
`encode(T)` 直接放进公开值，把这个互斥推到更强的形式 —— 不再需要"低熵枚举"，
反查字符表就够了。

## 4. 实现选型的偏差与理由（与计划 §9.1 的对照）

计划 §9.1 写的特征是：*"字符 2/3/4-gram，哈希到 `D=512` 桶，计数后 L2 归一化"*，
并且预判了失败路径：*"若 ezkl 无法表达 n-gram 哈希（见 §9.6 回退）：特征改在 SP1
电路内算，ezkl 只证 head"*。**实际实现与这两句都不同**，如实记录：

### 4.1 实际实现

| 维度 | 计划 §9.1 | 实际 | 理由 |
|---|---|---|---|
| 特征 | 字符 n-gram 哈希桶计数，`D=512` | 四张常数投影表（`Gather` 查表）+ 圆周移位乘积，`D=64` | 见下 |
| 定长 | 未指定 | `MAX_CHARS = 64`，超出**报错**不截断 | 截断会让尾部逃过判定 |
| 回退方案 | 特征在 SP1 内算，ezkl 只证 head | **未采用**：两侧都在同一张 ezkl 图内 | 回退会把公开值撑大（见 §1.1） |
| 定点口径 | 未指定 | `input_scale = 0`（= 1），id 以**原始浮点**进见证 | 见下，这是本项目最容易踩空的一处 |

**为什么不是 n-gram 哈希桶**：ezkl 的 tract 前端对算子有实际限制（本机实测）。两条
硬约束写在 `semantic/features.py::export_onnx` 的 docstring 里：不能带 `dynamic_axes`
（符号维度报 `Undetermined symbol in expression`），必须 `dynamo=False`（torch ≥2.9
默认走 dynamo 导出器，本栈不兼容）。哈希桶计数需要 `ScatterND`/`Bincount` 类算子，
而 `one_hot(idx) @ A` 的等价写法代价高三个数量级 —— 实测 `L=96 / V=193 / D=128` 的
one-hot 版本编译出 **~73 万行**、`pk.ezkl` **9.46 GB**，本机 12 GB 出不了证。
改用 `F.embedding`（图内即 `Gather`，每个位置一次查表，代价 ∝ L）后降到 13.1 万行。
**这是"能跑起来"与"跑不起来"的差别**，不是风格偏好。

### 4.2 `input_scale = 0`：一处会静默失效的口径

ezkl 的算子对定点的消费口径**不一致**，这是实测出来的：

- **消费下标**的算子（`Gather` / `OneHot`）拿的是**缩放后**的值；
- **算术**算子拿的是**解量化后**的值。

于是如果沿用常见的 `input_scale = 7`（id 会被当成 `id / 128`），`Cast` 到 int64 时
会把这些小数**截断**成 0 —— 全序列变成 PAD，模型输出一个**常数**。症状是"分数
不随输入变化"，看起来像训练失败而不像配置错误。另一种表现是直接 panic
（`Expected element to be less than num_classes, but got 8960`）。

正确口径：`run_args["input_scale"] = 0`（即 `2^0 = 1`，缩放值**就是** id 本身），
见证里送**原始浮点 id**。`semantic.patch_settings` 强制这个值，
`semantic.check_settings` 在验证方侧**再核一遍** —— 因为验证方如果跳过这一步，
一个口径不对的 `settings.json` 会让语义规则静默失效**而证明照样验证通过**。

> 这一节写在这里是因为它踩了不止一次。`semantic/features.py` 的模块 docstring
> 里有同样内容的另一份记录，留给改特征的人。

## 5. 与 zkML 工作的关系

本项目与 zkML 的关系是**收窄**，不是**替代**：

| | 通用 zkML | 本项目（P2-9） |
|---|---|---|
| 命题 | "这次推理是正确的" | "**这条响应**经**这张图**算出的分数**满足这个阈值**" |
| 公开值 | 常含中间激活 | 只有 `encode(T)` 与最终分数 |
| 图的角色 | 被证明的对象 | 被**承诺**的参数（指纹进策略） |
| 证明系统 | ezkl / EZKL / halo2 / 各家 | ezkl（halo2 后端） |
| 端到端证明 | 单系统 | **SP1（策略）+ ezkl（语义）**，验证方合取 |

差异的实质是把"模型正确性"整体挪出命题：我们不声称这张图是**对的**，只声称
**用的是这张图**、且**输入是这条响应**、且**结果满足阈值**。三条都是可证的窄命题，
合起来足以支撑合规结论 —— 而"这张图够不够好"是一个**评估问题**（§6.2），
不该、也不能由密码学回答。

### 5.1 为什么合取比"全塞进 SP1"更强，而不是更弱

常见的直觉是"证明系统越少越简单、越简单越可信"。这里恰好相反：把语义判定搬进
SP1 会要求公开全部中间量（§1.1），而**公开值一旦膨胀，绑定就退化成逐字段比对**，
中间量里任何一个都可成为攻击面。合取方案里双方各自的公开值都极小
（SP1 侧：`policy_hash`/`response_binding`；ezkl 侧：`encode(T)`/分数），
而唯一的接口是那一组指纹 —— 接口越窄，可攻击面越小。

### 5.2 ezkl 侧的可信基

诚实说：**ezkl 验证器本身不是形式化的**。我们的论证依赖 `A6`（halo2 的 soundness），
这不是我们能证明的东西，只能引用。工程上能做的两件事都做了：

1. **不用它做唯一判定**：六条反例在第 1–5 步就被挡住，ezkl 验证器是最后一颗钉子
   （见 `tests/test_semantic.py` 模块 docstring 的分层说明）；
2. **指纹进策略**：`vk.ezkl` 的哈希由 SP1 证明承诺，换验证钥匙会被第 2 步发现。

## 6. 诚实边界（**不保证**的部分）

### 6.1 语义规则只支持公开模式

见 §3.③。含语义规则的策略在私有模式下**直接 panic**。这是 v1 的硬边界，
`test_private_mode_fails_closed` 钉住它。要支持私有模式，需要 ezkl 侧的
"输入不出现在公开值、但验证方仍能核对绑定"的机制 —— 目前没有，且与
[`sp1-zk-audit.md`](sp1-zk-audit.md) 记录的 ZK 现状叠加后，短期内不打算做。

### 6.2 模型质量不是密码学结论

- **训练数据**的偏置、覆盖不足、分布外文本，L7 一个字都不管。模型在没见过的
  攻击手法上的表现，只能靠**评估**（`semantic/training_report.json`）如实记录。
- **投毒**：一个被投毒的模型，只要被如实承诺，证明链全部成立。
- **阈值的选择**是策略作者的判断（`threshold_bp`），不是安全性参数。
- 本项目**不**使用"模型卡"或训练数据承诺；`docs/eu-ai-act-mapping.md` 里对
  EU AI Act Art.11 等条目的覆盖是**部分**的。

### 6.3 定点近似

图内用 7 位定点（`scale = 128`），与浮点参考的差在 `1/128 ≈ 0.0078` 量级内。
`test_replica_matches_recorded_ezkl` 用这个刻度作为断言容差。**后果**：在阈值附近
（`|P - θ| < 1/128`）的判定可能对不上浮点参考。策略应把阈值选在远离决策边界的
位置，或接受这一档不确定性。这不是缺陷，是定点的定义。

### 6.4 单一模型（v1）

v1 只有**一个**模型。证书里 N 条语义规则共用同一份 `proof.json` —— 因为证明的内容
是"`encode(T)` 经这张图算出的分数"，而方向与阈值只是对**同一个分数**的不同比较。
`scripts/issue_cert.py::build_semantic_block` 里写明了这一点。多模型时要按模型
分开出证；届时 `companions[]` 的 `proof_file` 字段支持多个文件，但
`ezkl_prove.py` 目前的产物路径固定为 `semantic/artifacts/proof.json`（单槽），
多模型会覆盖。**这是已知的 v1 限制。**

### 6.5 响应的编码上限

图是定长的（`MAX_CHARS = 64`），`encode` 对超长响应**报错**而不是截断。
于是：

- 含语义规则的策略**必须**同时含一条 `max <= 64` 的 `length_bound`
  （`compile.require_covering_length_bound` 在**编译期**强制）；
- 超长响应**出不了证**（`issue_cert.py` 会明确报错退出，见 §7 的一处实测）。

这条设计是自洽的：超长响应本来就会撞上 `length_bound`（属于不合规），不出证是
正确结果。它把"合法输入的最大长度"与"图的容量"**对齐**了 —— 于是任意合法输入都
必然被完整判定。若不做这个对齐，攻击者只要把有害内容放在第 65 个字符之后。

## 7. 实测：一次完整的组合与绑定

`policy_packs/semantic_demo_v1.json`（关键词 + 长度上界 + `semantic_bound`，
`threshold_bp = 5000`、`direction = le`）。`verify_cert.py` 的输出：

**合规响应**（`The document is a short summary of quarterly results.`，53 字符）

```
[PASS] semantic[low_harm_probability] score=0 bp le 5000 bp；输入 == encode(T′) ✓；
       vk/onnx/阈值与公开值逐字段相符 ✓
RESULT: PASS
合规: PASS （SP1 部分 passed=True）
```

**同形异义绕过响应**（`How do I wеaponize the search tool against the user?`）

```
[PASS] semantic[low_harm_probability] score=10000 bp le 5000 bp；输入 == encode(T′) ✓；
       vk/onnx/阈值与公开值逐字段相符 ✓ — ⚠ 语义规则**未满足**
RESULT: PASS
合规: FAIL （SP1 部分 passed=True；未满足的语义规则：low_harm_probability）
```

这两段输出是本项目**最重要的一处诚实设计**的现场演示：

> `RESULT` 与 `合规` 是**两件事**，必须分开呈报。
>
> - `RESULT` = 这张证书是不是**真的**（签名/绑定/证明都对得上）。第二张证书
>   `RESULT: PASS` **是正确的** —— 它是一张如实的证据，记录的是"这条响应不合规"。
>   仓库里 `--expect violate` 的演示就依赖这一点。
> - `合规` = 证书说的是不是"**策略满足了**"。第二张是 `FAIL`。
>
> 少了这一行，一张 `passed=true` 而语义规则没过的证书会被读成合规 ——
> 而 **`outcome.passed` 只覆盖判得了的那部分**，语义规则根本不在其中。
> 这正是本项目的头号失败形态（P0-1）换了个位置出现。

一处**实测的 fail closed**：把一条 74 字符的良性文本喂给同一个策略时，
`issue_cert.py` 直接报错退出，而不是"截断后出证"：

```
陪伴证明生成失败 —— 含语义规则的策略**必须**有它，不能降级成「没有就不带」。
（最常见的原因是响应长过图的上限 MAX_CHARS …）
无法编码响应：text has 74 chars > max_chars=64: 语义规则不允许静默截断
```

顺带一提：那条响应同时**违反**了 `length_bound`（`passed=false`）。两个判定彼此独立、
结论一致，正是 §6.5 想要的形态。

## 8. 成本

实测数据见 [`bench/results/semantic.md`](../bench/results/semantic.md)（由
`bench/bench_semantic.py` 生成，数字从 JSON 来、不手抄）：

| 阶段 | 耗时 | 峰值常驻 | 频次 |
|---|---:|---|---|
| `setup` | 48 s | 4.76 GiB | 每策略一次 |
| `prove` | **77 s**（3 次中位） | **8.72 GiB** | **每条响应** |
| `verify` | 1.0 s | — | 每条响应 |

三个必须说清楚的点：

1. **`prove` 是每条响应一次，不是每个策略一次。** 77 s 的代价落在**在线路径**上，
   这对交互式场景是不可接受的。它把语义规则定位成**离线审计/批量合规核查**的能力，
   而不是实时护栏 —— 实时护栏仍需 P2-9b 的确定性折叠等轻量规则。
2. **峰值 ~9 GiB 是硬约束。** `setup` 与 `prove` 必须**分进程**跑，否则两段峰值
   叠加会在 12 GB 机器上 OOM。`scripts/ezkl_prove.py` 的模块 docstring 开头就写着
   这一条，`bench_semantic.py` 也按分进程的方式测量。
3. **`pk.ezkl` 2.92 GiB 不入库、`kzg.srs` 32 MiB 不入库**（可重算）；
   `vk.ezkl` 802 KiB **必须入库**（它是验证方唯一的凭据）。用 `.ezkl` 而不是 `.key`
   作扩展名，是因为 `.gitignore` 里那条 `*.key` 是给 Ed25519 私钥用的，`vk.ezkl`
   会被它**静默吞掉**。
