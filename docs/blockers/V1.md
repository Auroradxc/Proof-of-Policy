## 一句话

P2-03 的差分模糊测试在**受支持子集**上与 Python `re` 达到 **0 mismatch**，但
另外发现两条**实现 bug**，它们不是测试问题、也不是语义子集的取舍：

1. **G-1（T3 已记录）**：空字符类 `[^\d\D]` 被编译成 `Lit([])` → ε 边，
   **匹配空串**；Python 视为**空语言**。Rust 侧同样如此。
2. **V1-2（本次新发现）**：零次重复 `/a{0}/` 让 NFA 构造器抛
   `AttributeError: '_Builder' object has no attribute '_build'`，而 Python
   `re` 接受并匹配空串。

两条都在 `tests/test_fuzz_rules.py` 里**显式标注**（`expectedFailure` /
`assertRaises`），并写进 [`bench/results/fuzz.md`](../../bench/results/fuzz.md) 与
`fuzz.json`。没有静默跳过。

## G-1：空字符类是 ε 而不是 ∅（已知，T3 §12.3）

**复现**：

```python
from policydsl.core import nfa
spec = nfa.compile_pattern(r"[^\d\D]")
nfa.match_search(spec, "")        # True   ← bug：空语言匹配了空串
re.search(r"[^\d\D]", "") is not None   # False  ← Python：空语言
```

**根因**（`policydsl/core/nfa.py`）：

* `_parse_char_class` 取反后得到空区间列表，构造 `Lit([])`（`:145-148`）；
* `_Builder.build` 对 `Lit([])` 加一条 **ε 边**（`:315-317`）；
* 但 `_parse_concat` 的空连接也用 `Lit([])` 表示 ε（`:258-260`）。
  同一个表示同时承担「空语言 ∅」与「空串 ε」两种语义，后者是错的。

**为什么不是测试问题**：空字符类的语言按定义是 ∅；`re` 的语义是标准语义。
这是 NFA 的 AST/编译语义 bug，不是模糊测试挑了一个未支持的语法 —— 该模式
在文档声明的受支持子集内（「字符类 `[...]`，含区间与转义、取反 `[^...]`」）。

**影响**：定理 G(a)(b) 在空字符类上不成立；T3 已用假设 **A-G0**（字符类区间
非空）限定，[`docs/proofs/theorem-d-g.md`](../proofs/theorem-d-g.md) §12.3 / §19
把这条列为 G-1。

**修复建议（不在 V1 范围）**：把 AST 的「ε」与「空语言」分开（引入 `Empty`
与 `Eps`，或让 `Lit([])` 只表示 `Empty`、空连接用单独节点）；或者在解析器
直接**拒绝**空字符类（fail closed），并把 A-G0 写成解析器契约。两种都可，
但都必须同时改 Rust 侧并重建 vkey —— 因此 V1 不擅自修。

**实验证据**：

* `tests/test_fuzz_rules.py::TestEmptyCharacterClassGap`；
* `fuzz.json` 的 `g1.entries`：5 个模式 × 6 条文本 = 30 条，全部
  `known_gap: true`，方向固定为 `pike=True / re=False`；
* Rust 对拍：`test_g1_gap_is_shared_by_rust` 与 `fuzz.json.rust` 显示
  **Python 与 Rust 共有**该缺口（`python_vs_rust_mismatches = 0`，
  `rust_vs_re_mismatches` 的非零项正是 G-1）。

## V1-2：零次重复 `/a{0}/` 构造器崩溃（本次新发现）

**复现**：

```python
from policydsl.core import nfa
nfa.compile_pattern(r"a{0}")
# AttributeError: '_Builder' object has no attribute '_build'
re.search(r"a{0}", "xyz") is not None   # True（Python：零次重复 = ε）
```

**根因**（`policydsl/core/nfa.py`）：

* `_Builder._build_repeat` 在 `min=max=0` 时得到空片段列表 `parts = []`；
* `_chain([])` 走 `return self._build(Lit([]))`（`:371-373`）；
* 类里只有 `build`，没有 `_build` ⇒ `AttributeError`。

同类路径也可能影响 `{0,0}`（显式零次）。`{0,n}`（`n>0`）不会触发，因为
`parts` 至少含可选片段。

**为什么不是测试问题**：`{m}` 是文档声明支持的量词；`a{0}` 是合法正则，
Python 接受。这是实现里的方法名笔误 + 空片段路径未处理，不是「超出子集」。

**影响**：任何用户策略若写了 `{0}`（或 `{0,0}`）会在编译期崩溃（不是
`PolicyError` 的 fail-closed，而是未捕获的 `AttributeError`），表现为 500 /
进程崩溃而不是可读的语法拒绝。**不涉及证明健全性**（崩溃发生在出证前），
但属于可用性/错误处理缺陷。

**修复建议（不在 V1 范围）**：`_chain([])` 应返回一个显式的 ε 片段
（`s = new_state(); t = new_state(); s.eps.append(t)`），或直接拒绝零次重复；
顺便把方法名笔误改掉。修完要同步 Rust 侧并重建 vkey。

**实验证据**：`tests/test_fuzz_rules.py::TestZeroRepeatCrash` 用
`assertRaises(AttributeError)` 固定现状；`fuzz.json.known_crashes` 记录
`id: V1-2`。若将来修复，这两处会变红，提示同步更新。

## 与定理 E 的关系（不是新 bug，已有证明债）

P1-09 的 (c) 格复现了 T2 已记录的**实现-论文契约差距**：`verify_composite`
第 7 步绑的是 `derive(T_U) = input_from_response(T_U)`，不是用户提交的
`x_U`。因此当前组合只证弱形式

```
∃x: x = derive(T_U) ∧ T_U = M(x)
```

强形式 `x = x_U` **尚未落地**。这不是 V1 新发现的 bug，而是
[`docs/proofs/theorem-c-e-f.md`](../proofs/theorem-c-e-f.md) §2.7 的证明债
**E-1**；V1 只把它做成可复跑的负对照
（[`bench/results/composition_controls.md`](../../bench/results/composition_controls.md)）。

## 资源边界（不是 bug）

P1-11 在本机（24 核 / 14.6 GiB）实测到证明路径的 OOM 悬崖：

| 点 | cycles | prove | 峰值 RSS | 结果 |
|---|---:|---:|---:|---|
| pike n=100 | 643,906（实测） | 122.2 s | 11,695 MiB | 成功 |
| naive n=25 | ≈0.77 M（由 n=100 二次外推） | 153.2 s | 12,137 MiB | 成功 |
| naive n=50 | ≈3.1 M（由 n=100 二次外推） | 226.5 s | 13,772 MiB | **OOM / SIGKILL** |

naive n=100（~12.4 M cycles）与所有 n=400 的证明点留给云机。详表见
[`bench/results/dos_proof.md`](../../bench/results/dos_proof.md)。OOM 是**结果**，
不是实验失败，已如实保留。
