# X1e：6 规则 × 5000 的 core 可行性边界

> 状态：`done`（2026-11-01）。**6×5000 core 不可行（SIGKILL / OOM）**；
> 6×2000 与 6×3000 core 均可行（`verified=True`）。
> 分支 `bhv/x1e-6x5000`，基线 `025796b`。
> 云机 `connect.bjb2.seetacloud.com:37499`，host `autodl-container-14574f97ce-6e5bc639`；
> cgroup 16 核 / 92160 MB；binary `7f99fdb1…`；policy vkey `0x003eb14d…`；
> 构建基线 `e45178b`，**post-NFA-fix**；全部证明串行（`flock /tmp/pop-proof.lock`）。
> 环境与 blocker 详见 [X1e.md](../blockers/X1e.md)；上一轮见
> [X1d.md](../blockers/X1d.md) 与 [X1c.md](../blockers/X1c.md)。

本文件只回答一个问题：**在这台 90 GiB cgroup 上，6 条规则的 core 证明能推到多长**。
不改 core / cert / paper / circuits，只新增基准结果与实验记录。

## 1. 口径

- 规则集由 `bench_cycles.make_policy(6)` 构造（见
  [bench_scale.py](../../bench/bench_scale.py)）：1 条 `length_bound` + 3 条
  `keyword_block` + 2 条 `pattern_block`；pattern 用 `pike`（线性）匹配。
- 语料 `demo`（166 字符，来自 `scripts/examples/eu_agent_reply.txt`），平铺到目标长度，
  且保证不命中任何规则（`passed=True`，扫描跑到底而不是命中即停）。
- 每点一个独立子进程；外层 `timeout 900`；单进程、一次一个证明。
- 2000/3000 两个补点是为定位上界而加，按协议**最多两个**；没有再细分 4000。

## 3. 读法

### 3.1 6 规则的最大可行长度

- **3000 可行、5000 不可行**，因此在本机 90 GiB cgroup 下，6 规则的可行长度上界
  落在 **[3000, 5000)** 区间内；按 1000 字符的粒度，**已证最大可行长度是 3000**。
- 2000 → 3000 的峰值内存从 **36.9 GB 涨到 48.7 GB**（+11.8 GB / +1000 字符），
  说明规则数固定为 6 时，长度仍是一个很陡的二次型成本项；按这个斜率外推，
  4000 字符已接近 60 GB 以上，5000 撞上 90 GiB 墙并不意外。
- 时间也从 117.11 s 涨到 139.66 s；5000 在 157.74 s 被杀，**不是超时**
  （`timeout 900` 远未到），是内存墙先到。

### 3.2 5000 为什么在 RSS 67.5 GB 时就 OOM

先纠正一个口径：**67.5 GB 与 96.6 GB 不是同一时刻、同一口径的两个数**。

1. 67.5 GB 是 155 s 的**一次采样**（`ps rss`，十进制 GB；= 64.4 GiB），不是峰值。
   `/usr/bin/time -v` 在 SIGKILL 下不打印 Max RSS，因此 5000 **没有**可入库的峰值数字；
   这是量测限制，不是 0。
2. **同一时刻** cgroup `memory.current` 已经是 **94.9 GB**（= 88.4 GiB），离
   `memory.max` 96.6 GB（90 GiB）**只剩 1.75 GB**。
3. 149 → 155 s 这 6 秒里，cgroup 从 78.6 GB 涨到 94.9 GB（**+2.72 GB/s**），
   进程 RSS 同期 +16.1 GB。按这个速率，1.75 GB 余量 **0.6 s** 就烧完；进程在采样后
   又活了 2.7 s 才被杀，说明中间靠回收页缓存多撑了约 2 s。
4. 67.5 GB 到 96.6 GB 之间那 ~29 GB **不是空闲内存**，而是同一 cgroup 里已经记在
   别人/缓存账上的部分：

| 项目（155 s 时刻估算） | 量 | 证据 |
|---|---:|---|
| prover RSS（采样，非峰值） | 67.5 GB | `ps rss` |
| E1 的 Qwen 采样进程 anon | ~3.4 GB | 该进程全程存活，现 RSS 3.38 GB |
| 其它容器进程（sshd/supervisord/autopanel/tensorboard/下载…） | ~0.3 GB | 当前 `ps` |
| 内核 slab + shmem + 栈/sock | ~1.6 GB | `memory.stat`：slab 0.69 + shmem 0.87 |
| 文件页缓存（HF 模型活跃页、Mistral 下载、repo 工件） | ~22 GB | `memory.current` − 以上；当前 `file` 已 30 GB |
| 合计 = cgroup `memory.current` | **94.9 GB** | `memory.current` |

   HF 缓存本身 **45 GB**（Qwen2.5-7B 15 GB + 正在下载的 Mistral-7B 31 GB），
   E1 在本轮期间持续推理/下载；这些文件页都记在**同一个 cgroup** 上。
5. **没有 swap**：`memory.swap.max = 0`，anon 峰值不能换出，唯一缓冲是页缓存。
6. 内核侧证据：`memory.events` = `max 277508 / oom 0 / oom_kill 0`，且
   `dmesg_restrict=1`（读不到内核日志）。也就是说，**在这个 cgroup 里，内核 OOM
   killer 没有留下足迹**。因此更准确的表述是：进程在 cgroup 已用 94.9/96.6 GB、
   且以 ~2.7 GB/s 继续分配时被 **SIGKILL**；触发者可能是容器外的平台内存守卫
   （按配额 ~95–98% 杀最大进程），也可能是不可见的上层 cgroup/host 层，容器内
   无法区分。仓库自己的 `policydsl/runtime/service.py` 也写明 SIGKILL「多半是
   OOM killer，也可能是别人 `kill -9`」。
7. **不是 SP1 自带的 memory monitor**：SP1 6.7 的 `spawn_restricted` 只对 executor
   **子进程**按 `MEMORY_LIMIT`（默认 24 GB、每 100 ms 采样）发 SIGKILL，并以
   `KilledByMemoryMonitor` / `ChildKilled` 错误返回；顶层 prover 没有这个机制，
   且 `ps` 采样里没有 executor 子进程。它解释不了顶层 137。

**结论**：OOM 的物理原因是**内存耗尽**，不是「67.5 GB 还有 29 GB 余量」。RSS 是
被杀前 2.7 s 的采样、且只是进程口径；同刻 cgroup 余量只有 1.75 GB，进程正以
~2.7 GB/s 增长，页缓存回收速度跟不上（HF 模型与下载还在持续产生活跃/脏页），
随后被 SIGKILL。SIGKILL 是内核 OOM 还是平台外部 kill，受 `dmesg_restrict=1` 和
`oom_kill=0` 限制无法在容器内定论，但现有证据**更支持外部 kill**。

本实验按协议不 drop caches（会干扰同机 E1 的模型缓存），故**不排除**在更干净的
缓存状态下 5000 有通过的可能；但按本次实测，**5000 core 不可证**。
- 与 X1d 的 10000/50000 两点对照：那两点在 ~100 s 就被杀，而 5000 坚持到 157.74 s。
  时间到墙的变化与「文本越长、单位时间内存增长越快」一致；长度不是主变量的说法
  只适用于 10000 与 50000 之间，不适用于 5000。

### 3.3 未做的点

- **6×5000 groth16 未跑**：按协议 core 不可证就不进入 groth16（后者还要叠加
  ~20 GB 包装开销）。这里的 OOM 是 core 先撞墙，不是 groth16 不行。
- **未细分 4000**：补充点按协议上限两个（2000/3000），4000 留作后续。
  因此上界是区间 `[3000, 5000)`，而不是一个具体数字。

## 6. 结论

**6 规则 × 5000 core 在这台 90 GiB cgroup 上不可行（157.74 s 被 SIGKILL）；6 规则的
最大可行长度已证到 3000（117–140 s / 37–49 GB，均 `verified=True`），上界在
`[3000, 5000)`。** 这是内存墙，不是超时：5000 被杀时 cgroup 已用 94.9/96.6 GB
（余量 1.75 GB），进程仍在以 ~2.7 GB/s 分配；容器内 `oom_kill=0`，SIGKILL 的
来源更可能是平台外部守卫而非内核 cgroup OOM。
