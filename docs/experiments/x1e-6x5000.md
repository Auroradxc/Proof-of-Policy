> 状态：`done`（2026-11-01）。**6×5000 core 不可行（SIGKILL / OOM）**；
> 6×2000 与 6×3000 core 均可行（`verified=True`）。
> 分支 `bhv/x1e-6x5000`，基线 `025796b`。
> 云机 `connect.bjb2.seetacloud.com:37499`，host `autodl-container-14574f97ce-6e5bc639`；
> cgroup 16 核 / 92160 MB；binary `7f99fdb1…`；policy vkey `0x003eb14d…`；
> 构建基线 `e45178b`，**post-NFA-fix**；全部证明串行（`flock /tmp/pop-proof.lock`）。
> 环境与 blocker 详见 [X1e.md](../blockers/X1e.md)；上一轮见
> [X1d.md](../blockers/X1d.md) 与 [X1c.md](../blockers/X1c.md)。

本文件只回答一个问题：**在这台 90 GiB cgroup 上，6 条规则的 core 证明能推到多长**。
不改 core / cert / paper / circuits，只新增基准结果与实验记录。

## 1. 口径

- 规则集由 `bench_cycles.make_policy(6)` 构造（见
  [bench_scale.py](../../bench/bench_scale.py)）：1 条 `length_bound` + 3 条
  `keyword_block` + 2 条 `pattern_block`；pattern 用 `pike`（线性）匹配。
- 语料 `demo`（166 字符，来自 `scripts/examples/eu_agent_reply.txt`），平铺到目标长度，
  且保证不命中任何规则（`passed=True`，扫描跑到底而不是命中即停）。
- 每点一个独立子进程；外层 `timeout 900`；单进程、一次一个证明。
- 2000/3000 两个补点是为定位上界而加，按协议**最多两个**；没有再细分 4000。

## 3. 读法

### 3.1 6 规则的最大可行长度

- **3000 可行、5000 不可行**，因此在本机 90 GiB cgroup 下，6 规则的可行长度上界
  落在 **[3000, 5000)** 区间内；按 1000 字符的粒度，**已证最大可行长度是 3000**。
- 2000 → 3000 的峰值内存从 **36.9 GB 涨到 48.7 GB**（+11.8 GB / +1000 字符），
  说明规则数固定为 6 时，长度仍是一个很陡的二次型成本项；按这个斜率外推，
  4000 字符已接近 60 GB 以上，5000 撞上 90 GiB 墙并不意外。
- 时间也从 117.11 s 涨到 139.66 s；5000 在 157.74 s 被杀，**不是超时**
  （`timeout 900` 远未到），是内存墙先到。

### 3.2 5000 的 OOM 观察

- `/usr/bin/time -v` 在 SIGKILL 下不会打印 `Maximum resident set size`，因此
  5000 这一行**没有**可入库的峰值内存；这是量测限制，不是 0。
- 被杀前的运行中采样（155 s）：进程 RSS **67.5 GB**；同期 cgroup
  `memory.current` **94.9 GB**，`memory.max` = **96.6 GB**。约 2.7 s 后进程收到
  SIGKILL。直接触发点是 cgroup 内存上限。
- 需要注意的口径事实：67.5 GB RWSS 距 96.6 GB 上限仍有约 29 GB，其中包含此前
  rsync/页面缓存等**可回收的 file cache**。因此这次 OOM 的机制是「anon 工作集增长 +
  最后阶段分配尖峰 + 页缓存」共同撞上 cgroup 上限，而不是「anon 单独就吃满了 90 GiB」。
  本实验按协议不 drop caches（会干扰同机 E1 的模型缓存），故**不排除**在更干净的
  缓存状态下 5000 有通过的可能；但按本次实测，**5000 core 不可证**。
- 与 X1d 的 10000/50000 两点对照：那两点在 ~100 s 就被杀，而 5000 坚持到 157.74 s。
  时间到墙的变化与「文本越长、单位时间内存增长越快」一致；长度不是主变量的说法
  只适用于 10000 与 50000 之间，不适用于 5000。

### 3.3 未做的点

- **6×5000 groth16 未跑**：按协议 core 不可证就不进入 groth16（后者还要叠加
  ~20 GB 包装开销）。这里的 OOM 是 core 先撞墙，不是 groth16 不行。
- **未细分 4000**：补充点按协议上限两个（2000/3000），4000 留作后续。
  因此上界是区间 `[3000, 5000)`，而不是一个具体数字。

## 4. 串行、隔离与 E1

- 三次证明逐次串行，统一 `flock /tmp/pop-proof.lock`；未与其他出证任务并发。
- 使用独立目录 `/root/autodl-tmp/zk-policy-x1e`（rsync worktree，排除
  `.git`/`circuits/target`/`.claude`/`bench/results`/`scripts/examples/out`），
  `pop-script` 软链到共享 checkout 的 release binary；未修改 `zk-policy-x1d` /
  `zk-policy-e1`。
- **E1 未受影响**：E1 的 Qwen 采样进程（`bench_k_entropy.py`，CUDA）在本轮全程存活，
  GPU 利用率 72–80%、显存 15.2 GiB；本实验只用 CPU、未 kill 任何进程、未碰 GPU。
  X1d 遗留的一个 `zk-policy-x1d` core 证明进程在本轮开工前自行结束（非本实验 kill），
  之后才启动本轮第一个点。

## 6. 结论

**6 规则 × 5000 core 在这台 90 GiB cgroup 上不可行（157.74 s 被 SIGKILL）；6 规则的
最大可行长度已证到 3000（117–140 s / 37–49 GB，均 `verified=True`），上界在
`[3000, 5000)`。** 这是内存墙，不是超时；5000 的直接触发点是 cgroup 96.6 GB 上限。
