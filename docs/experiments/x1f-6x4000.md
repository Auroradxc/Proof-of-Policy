## 1. 口径

- 规则集由 `bench_cycles.make_policy(6)` 构造（见
  [bench_scale.py](../../bench/bench_scale.py)）：1 条 `length_bound` + 3 条
  `keyword_block` + 2 条 `pattern_block`；pattern 用 `pike`（线性）匹配。
- 语料 `demo`（166 字符，来自 `scripts/examples/eu_agent_reply.txt`），平铺到目标长度，
  且保证不命中任何规则（`passed=True`，扫描跑到底而不是命中即停）。
- 每点一个独立子进程；外层 `timeout 900`；单进程、一次一个证明；**不 drop caches**
  （会干扰同机 E1 的模型缓存）。
- 与 X1e 保持同一台机器、同一个 binary sha256、同一条规则集/语料/环境变量，
  因此 3000 / 4000 / 4500 / 5000 四个点可以直接并列读。
- 主点是 4000；4500 是任务允许的**一次**可选收窄点（4000 成功后才跑）。
  5000 不重跑：X1e 已判 OOM，本实验不重复撞墙。

## 3. 读法

### 3.1 6 规则的边界：从 `[3000, 5000)` 收窄到 `[4500, 5000)`

- **4000 可行、4500 可行、5000 不可行**，所以瓶颈落在 **`[4500, 5000)`**；
  按 500 字符的粒度，**已证最大可行长度是 4500**。
- 3000 → 4000：峰值 RSS **+10,532.6 MB / +1000 字符**（48,683.9 → 59,216.5 MB），
  耗时 +22.71 s。
- 4000 → 4500：峰值 RSS **+5,008.2 MB / +500 字符**（= +10,016.4 MB / +1000 字符），
  耗时 +19.29 s。
- 也就是说，在 3000–4500 这一段，成本仍近似**线性**（约 10.0–10.5 GB / 1000 字符），
  并没有出现 5000 处那种「突然撞墙」的形状；5000 的失败更像是所需 anon 峰值
  **超过了 96.6 GB 减去不可回收缓存**，而不是曲线提前拐弯。
- 4500 的成功余量极小：cgroup 峰值距 `memory.max` 只有 **20,480 B**（见 §3.2）。
  这使 `[4500, 5000)` 的结论**对页缓存条件敏感**，不能读成「4500 在任何机器状态下
  都稳过」。

### 3.2 cgroup / 页缓存条件与 `memory.events`

**开工前条件（两次运行前分别采样）**：

| 项目 | 4000 开工前（21:53:33） | 4500 开工前（21:59:55） |
|---|---:|---:|
| cgroup `memory.current` | 35.41 GB | 34.47 GB |
| cgroup `memory.max` | 96.64 GB（90 GiB） | 96.64 GB（90 GiB） |
| 文件页缓存（`memory.stat file`） | 31.42 GB | 30.48 GB |
| anon | 3.27 GB | 3.27 GB |
| slab / shmem | 0.69 GB / 0.87 GB | 0.69 GB / 0.87 GB |
| `memory.swap.max` | 0 | 0 |
| `memory.events` | max 277,508 / oom 0 / oom_kill 0 | max 284,155 / oom 0 / oom_kill 0 |
| E1（Qwen2.5-7B，CUDA） | 存活，RSS 3,375,984 KB，GPU 88% / 15,205 MiB | 存活，RSS 3,367,204 KB，GPU 80% / 15,205 MiB |
| HF 缓存 | 45 GB | 45 GB |

**运行中（每 5 s 采样进程 RSS、cgroup `memory.current`、`memory.events`、
E1 RSS 与 GPU）**：

- **4000**：cgroup 峰值 **94.36 GB**（21:57:37），余量 **2.27 GB**；同刻进程采样
  RSS 57,490,772 KB，cgroup anon 62.10 GB，文件页缓存 31.42 GB。约 21:58:35 出现
  第二次上冲，`memory.events` 的 **max 计数 +6,647**（277,508 → 284,155），
  内核在 5 s 采样间隙触顶并回收，页缓存最低降到 **30.47 GB**（约 −0.95 GB）；
  `oom=0 / oom_kill=0`，随后正常完成。
- **4500**：cgroup 峰值 **96.637 GB**（22:01:26），距 `memory.max`
  **仅 20,480 B**；同刻进程采样 RSS 62,759,324 KB，cgroup anon 67.50 GB，
  文件页缓存 28.29 GB；下一采样（22:01:31）进程采样 RSS 升到 63,885,732 KB。
  `memory.events` 的 **max 计数 +37,185**（284,155 → 321,340），页缓存从开工前的
  30.48 GB 被回收到最低 **25.21 GB**（**−5.27 GB**）；`oom=0 / oom_kill=0`，
  没有触发 OOM，最终 `verified=True`。

**怎么读 `memory.events`**：

- `max` 是「分配需求撞到 `memory.max`、内核尝试回收」的累计计数，
  **不等于 OOM**。4000 与 4500 都把它推高了数千到数万次，但 `oom` 与
  `oom_kill` 始终是 0，进程正常完成。
- 因此本轮的准确表述是：**4500 是靠回收约 5.27 GB 文件页缓存才在 90 GiB 墙边
  拿到证明的**；如果同一时刻可回收缓存更少（例如 E1 的活跃/脏页更多、或缓存已
  被别的 cgroup 账目占满），4500 有实质 OOM 风险。反过来，缓存更干净时 5000
  也许有通过的可能——但这是未验证的假设，按本轮实测 5000 仍不可证。
- 容器内 `oom_kill=0` 且 `dmesg_restrict=1`，所以**无法在容器内区分**内核 cgroup
  OOM 与容器外平台守卫的 kill；这一限制与 X1e 相同。

### 3.3 5000 的 OOM 机制（与 X1e 对照）

X1e 的 6×5000 在 157.74 s 被 SIGKILL：155 s 采样时进程 RSS 67.5 GB（非峰值），
同刻 cgroup `memory.current` 94.9/96.6 GB（余量 1.75 GB），149→155 s cgroup 以
约 2.72 GB/s 增长；`memory.swap.max=0`，`oom=0 / oom_kill=0`。

本轮补充了「撞墙但不死」的对照：4000/4500 都触发了 `memory.events.max`
（分别 +6,647 / +37,185），却都靠页缓存回收活了下来。所以 5000 的 SIGKILL
**不是「碰一次 memory.max」就会发生**；它更像是持续 anon 增长耗尽了可回收缓存之后
仍有分配需求。按本轮 4000→4500 的斜率外推，5000 的进程峰值约在 69–70 GB，
比 4500 再多约 5 GB anon——这正好接近 4500 已经动用的 5.27 GB 缓存余量。
**外推不是测量**：5000 未重跑，具体是内核 OOM 还是平台外部 kill 仍无法在容器内定论；
可以确定的是内存墙先到，`timeout 900` 远未到。

### 3.4 量测限制

- **4000 的 5 s 原始采样日志被 4500 的采样器覆盖**（生成 4500 采样脚本时，
  输出路径没有随文件名替换干净）。4000 的关键采样值已在本节与 JSON `provenance.sampling`
  中逐条记录，但原始逐行序列未保留。4500 的原始采样保留在云机
  `/root/autodl-tmp/x1f-work/sample-6x4500.log`，未入库。
- 5 s 采样会漏掉瞬时峰值；成功点的权威峰值来自 `/usr/bin/time -v` 的
  `Maximum resident set size`（表中 MB 实为 kbytes/1024，即 MiB）。
  SIGKILL 下 `time -v` 不打印 Max RSS，所以 5000 没有峰值数字。
- 第一次 4000 启动时，外层 shell 在 fork 证明子进程之前挂住（未跑任何证明）；
  该 shell 被终止后用 `setsid` 重新启动，正式计时从 21:56:11 开始。
- 4500 距上限只有 20 KB，单次运行的成功不足以断言「4500 在任意缓存状态下都可证」；
  它证明的是「在本轮 E1/页缓存条件下可证」。

## 4. 串行、隔离与 E1

- 两个点逐次串行，统一 `flock /tmp/pop-proof.lock`；一次只跑一个证明，未与其他
  出证任务并发。使用独立目录 `/root/autodl-tmp/zk-policy-x1f`（rsync worktree，
  排除 `.git`/`circuits/target`/`.claude`/`bench/results`/`scripts/examples/out`），
  `circuits/target/release/pop-script` 软链到共享的
  `/root/autodl-tmp/zk-policy/circuits/target/release/pop-script`（sha256
  `7f99fdb1…`，与 X1e 相同）；未修改 `zk-policy-x1d` / `zk-policy-x1e` /
  `zk-policy-e1`。
- **E1 未受影响**：E1 的 Qwen 采样进程（`bench_k_entropy.py`，CUDA）在两次运行中
  全程存活，GPU 利用率 69–88%、显存 15.2 GiB；开工时 E1 还有一个 Mistral
  tokenizer 进程。本实验只用 CPU、未 kill 任何进程、未碰 GPU、未 drop caches。
- E1 的 Qwen anon（约 3.37 GB）与 45 GB HF 缓存带来的约 30–31 GB 文件页缓存
  **记在同一个 cgroup 上**，构成本轮最关键的外部条件：它既是压力（压缩余量），
  也是缓冲（4500 靠回收其中 5.27 GB 过关）。


采样（与运行并行，5 s 一次）：进程 RSS、cgroup `memory.current` / `memory.stat` /
`memory.events`、E1 RSS、GPU 利用率。`memory.max` 与 `memory.swap.max` 在开工前记录。

## 6. 结论

**6 规则 × 4500 core 在这台 90 GiB cgroup 上可行（181.66 s / 64,224.7 MB /
`verified=True` / `passed=True`），4000 同样可行（162.37 s / 59,216.5 MB）；
因此 6 规则的可行上界从 `[3000, 5000)` 收窄为 `[4500, 5000)`。** 5000 仍按 X1e
判为 OOM。本轮的关键条件是页缓存：4500 在距 `memory.max` 仅 20,480 B 处靠回收
5.27 GB 文件页缓存过关，`memory.events` 的 max 计数 +37,185 而 `oom/oom_kill=0`；
结论依赖 E1 同 cgroup 的约 30 GB 可回收页缓存，不能外推到缓存更紧的机器状态。
